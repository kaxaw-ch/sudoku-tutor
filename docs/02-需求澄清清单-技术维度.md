# 技术澄清清单与可行性评估

> 项目：数独教学跨端游戏 | 编制：高见远（架构师） | 日期：2026-08-05
> 依据文档：《数独教学跨端游戏 开发需求说明书》
> 本文档仅做**技术澄清与风险评估**，不含架构设计与代码。

## 摘要

本项目在**算法层面是可行的**，需求书本身写得相当专业，技巧清单、分层规范、测试要求都体现出提出方懂行。但在**交付形态、谜题供给、教学判定**这三处存在被严重低估甚至无法实现的部分。

### 技术上最大的三个风险

| # | 风险 | 严重度 | 本质 |
|---|---|---|---|
| R1 | **构建交付链路完全为零** | 🔴 极高 | 当前开发机上 Flutter / Dart / JDK / Android SDK / Visual Studio / Windows SDK **无一安装**。而 Windows exe 与 Android apk 是合同必交物。工具链需新增约 20–28 GB 安装量，其中 Visual Studio 需管理员权限与 UAC 交互，本会话沙箱已证实不具备该权限。**这是唯一可能直接卡死交付的风险，且与代码能力无关。** |
| R2 | **两项核心需求当前措辞下不可实现** | 🔴 极高 | ①「按难度生成唯一解、且恰好需要某高级技巧才能解开的谜题」——运行时实时生成在数学期望上不可行（生成一道"必须用 Swordfish"的题需试数百至数万次）；②「强制校验玩家必须通过目标技巧完成关键删数，猜数绕过则判不通过」——玩家的**心理推理过程不可观测**，严格意义上无法 100% 判定。二者都必须降级，且降级方案需客户书面确认。 |
| R3 | **技巧识别引擎工作量被低估约 2–3 倍** | 🟡 高 | 10 项技巧中，X-Wing / Swordfish / XY-Wing / XYZ-Wing 是教科书式好实现；但 **基础 AIC 一项的工作量约等于其余九项之和**，且「基础 AIC」「W-Wing 的强链」「Finned 是否含 Sashimi」「UR 成立前提」在业界存在**实现口径分歧**，不确认口径就开发必然返工。此外需求书未计入的隐性工作量还有：讲解文案生成、可视化数据结构、离线出题工具、带标注的测试盘面集。 |

### 0.4 关于「我方能否自动安装」的诚实评估

本会话运行在受限沙箱中，实测过程中已观察到两处硬性限制：

1. 执行 `vswhere.exe` 被安全策略直接阻断（`Command blocked for security: Known Windows LOLBin`）；
2. 对 `%USERPROFILE%\.workbuddy\logs` 路径的访问被沙箱拦截并遭用户拒绝。

结合安装本身的性质：

- **Visual Studio 工作负载**安装需要**管理员权限 + UAC 弹窗确认**，无法在当前沙箱内静默完成；
- **Android SDK 许可协议**需交互式逐条接受（`flutter doctor --android-licenses`）；
- 三项大件合计 20–28 GB 下载，耗时以小时计。

**结论：工具链安装必须由客户方 / 机器所有者手动介入完成，或由客户明确授权我方在非沙箱环境下以管理员身份执行安装脚本。**
我方可交付一份**完整的、可复制粘贴执行的安装脚本 + 逐项验收命令清单**（含 winget 命令、环境变量配置、`flutter doctor -v` 期望输出），但不能承诺在当前会话环境中自动完成。

## 一、🔴 技术红线（做不到 / 需要客户提供资源，必须告知）

### T-01　macOS / iOS 产物在 Windows 机器上物理不可构建

- **性质**：Apple 平台硬性限制，非能力或工期问题。
- **事实**：编译 iOS/macOS 应用必须调用 Xcode 工具链，Xcode 仅运行于 macOS。Flutter 官方文档明确要求 iOS/macOS 构建宿主为 macOS。
- **额外依赖**：iOS 真机运行与分发还需 Apple Developer Program 账号（99 USD/年）、开发/分发证书、Provisioning Profile、App ID。
- **客户需决策（三选一）**：
  - **A. 提供 Mac 硬件**（Mac mini 即可）+ Apple 开发者账号 → 我方可完成 macOS/iOS 适配与打包。
  - **B. 采购 Mac 云构建服务**（如 Codemagic / MacStadium），客户承担费用与账号 → 可交付，但需客户账号授权。
  - **C. 移出交付范围** → 我方仅保证代码层面对 iOS/macOS 的兼容性（不使用平台特有 API、布局响应式），交付「可在 Mac 上构建的源代码」，但**不交付 macOS/iOS 可运行产物，也不承担在 Mac 上首次构建可能出现的适配问题**。
- **我方推荐**：**方案 C**（本期移出），待客户具备 Mac 环境后作为独立变更单追加。理由：P0 的 Windows+Android 双端已足够验证产品，Mac 环境的引入会显著增加环境成本与调试面，不宜与首期交付耦合。

### T-02　当前开发机不具备任何构建能力，工具链安装需客户介入

- **事实**：见第零节实测。Flutter / Dart / JDK / Android SDK / Visual Studio / Windows SDK / Ninja **全部缺失**。
- **影响**：在补齐前，**连 P0 的 Windows exe 和 Android apk 都无法产出**，也无法执行 `flutter test`。
- **成本**：约 20–28 GB 下载安装，视网速需 1–4 小时；C 盘剩余 136 GB 够用但建议清理至 ≥ 40 GB 可用余量。
- **阻碍**：Visual Studio 需管理员权限 + UAC 交互；Android SDK 需交互式接受许可协议；当前沙箱会话已被证实不具备无限制系统安装权限。
- **客户需决策**：
  - 由客户方 IT / 机器所有者按我方提供的清单**手动安装**；**或**
  - 客户**明确书面授权**我方在非沙箱、管理员权限下执行安装脚本。
- **我方承诺**：无论选哪种，我方交付一份完整安装脚本 + 验收命令清单，并以 `flutter doctor -v` 全项通过作为 M0 验收标准。

### T-03　Android Release 签名密钥必须由客户提供

- **事实**：`flutter build apk` 默认使用 **debug 签名**。debug 签名的 apk：可安装可运行，但**不可上架任何应用商店**，且 Google 明确标记为不可分发。
- **客户需决策**：
  - **A. 只需内部测试/侧载** → 交付 debug 签名 apk 即可，**无需客户提供任何东西**。
  - **B. 需要正式分发/上架** → 客户须提供 **release keystore 文件 + storePassword + keyPassword + keyAlias**；或授权我方生成后**将 keystore 与密码一并移交客户妥善保管**（⚠️ keystore 一旦丢失，该应用将**永久无法发布更新**，这是 Android 生态的不可逆约束，必须让客户知晓）。
- **我方推荐**：本期按 **A（debug 签名）** 交付以避免密钥托管的法律与安全责任；若客户需要 B，请在 M0 前提供 keystore。

### T-04　「强制校验玩家必须使用目标技巧」严格意义上无法 100% 实现

- **事实**：系统只能观测玩家的**操作事件流**（填了什么数、删了哪些候选数、点了哪些格子）。**玩家脑中的推理过程不可观测。** 一个真正用 X-Wing 推理的玩家，与一个背下了答案或蒙对了的玩家，可以产生**完全相同的操作序列**。因此"判定玩家是否真的使用了 X-Wing"在信息论意义上不可判定。
- **可落地的降级方案**：详见 §3.3，核心是把"不可观测的心理行为"转化为"可观测的 UI 行为"。
- **客户需确认**：接受降级判定口径（§3.3 给出完整文案），并确认是否接受为此新增「模式指认」交互。
- **我方立场**：这一点必须现在说清。若合同写死"系统能识别玩家是否猜数"，验收时必然扯皮。

### T-05　「实时生成必须用某高级技巧才能解开的谜题」不可行

- **事实**：随机生成 + 技巧过滤（reject sampling）对高级技巧的命中率极低。以 Swordfish 为例，"该技巧为解题所必需且无更简单替代路径"的谜题在随机盘面中占比通常在 **0.1%–1%** 量级；UR / W-Wing / 特定 AIC 更低，可低于 0.1%。详见 §3.2 定量分析。
- **影响**：运行时在手机上现场生成一道"必须用 Swordfish"的题，期望耗时可达**数分钟至一小时**，且结果不可控。**这条路必须放弃。**
- **降级方案**：改为**离线预置盘面库**（详见 §3.2 与 T-10）。
- **附带工作量**：需额外开发一个**离线出题工具**（Dart CLI，复用算法层，在 PC 上跑数小时批量产出盘面库 JSON）。这是需求书**未计入**的交付物，约 2–3 人日。

### T-06　品牌与法务资产客户未提供

需求书通篇未提及以下必需项，全部需要客户提供或授权我方代为处理：

| 项 | 说明 | 缺失后果 |
|---|---|---|
| **应用包名 / Bundle ID** | 如 `com.<客户域名>.sudokututor`。**必须使用客户拥有的域名反写** | `com.example.*` 被 Google Play **直接拒绝**；后期修改包名等同于换一个新应用，无法覆盖安装 |
| **应用名称** | 中文显示名 + 英文名 | 只能用占位名 |
| **应用图标** | 各平台多尺寸（Android 自适应图标、Windows .ico） | 只能用 Flutter 默认图标 |
| **启动图 / 品牌色** | — | 使用默认样式 |
| **中日韩字体** | 若需跨平台一致的中文渲染，需内置 CJK 字体（如 Noto Sans SC，全量约 10 MB，子集化后 1–3 MB）。**需确认字体授权** | 依赖各平台系统字体，Windows/Android/iOS 中文渲染效果不一致 |
| **隐私政策 URL** | 仅在上架应用商店时必需 | 无法上架 |

**我方推荐**：若本期仅内部交付，全部使用占位资产并在文档中标注替换方法；若需上架，请客户在 M0 前提供。**包名必须现在确定**，这是唯一一个后期修改代价极高的项。

### T-07　P2「每日一题排行榜」与 P0「完全离线」直接冲突

- **事实**：排行榜需要服务端（题目下发、成绩上报、排名计算、防作弊）、网络权限、用户身份体系。而需求书 §2.5 与 §4 两处明确要求「完全离线」。
- **影响**：一旦引入网络，Android 需申请 `INTERNET` 权限、需提供隐私政策、iOS 需应对 ATT 合规；「完全离线」的宣称不再成立。
- **客户需确认**：P2 是否确实在本合同范围内？
- **我方推荐**：**P2 明确移出本期合同**，作为后续独立项目。本期在架构上仅保证"不阻塞未来接入"（数据层留接口），但不实现、不预留服务端工作量。「每日一题」若想保留离线形态，可降级为**基于日期种子从本地题库确定性选题**（无排行榜、无联网），这个是零成本可做的，建议采纳。

### 3.2 谜题生成器可行性分析

#### 3.2.1 标准生成流程与实际成本

| 步骤 | 方法 | 单次耗时（PC，Dart AOT） | 可行性 |
|---|---|---|---|
| ① 生成完整合法终盘 | 随机化回溯填充 | < 1 ms | ✅ 无问题 |
| ② 挖洞 + 唯一解校验 | 逐格挖空，每次挖后做"解数计数（found 2 即中止）" | 约 50–60 次求解，合计 **100–300 ms** | ✅ 可接受 |
| ③ 难度评级 | 用人类技巧求解器逐步求解，记录所需最高技巧 | **10–500 ms**（含 AIC 时显著变慢） | ✅ 单次可接受 |
| ④ **筛选出"恰好需要技巧 X"** | **拒绝采样**：不符则丢弃重来 | 🔴 **见下** | ❌ **不可行** |

#### 3.2.2 拒绝采样的期望成本（核心问题）

关键在于命中率。在随机生成的谜题中，**某高级技巧成为"解题所必需、且无更简单替代路径"** 的概率非常低——因为一旦盘面上出现 Swordfish，通常同时也存在 XY-Wing 或涂色等更简单的解法，求解器会优先用简单技巧解掉，导致该题被评级为更低难度。

| 目标技巧 | "严格必需"的大致命中率 | 期望试验次数 | 单次成本约 0.3 s 时的期望耗时 |
|---|---|---|---|
| X-Wing | 约 1%–5% | 20 – 100 | 6 秒 – 30 秒 |
| Swordfish | 约 **0.1%–1%** | **100 – 1,000** | **30 秒 – 5 分钟** |
| XY-Wing / XYZ-Wing | 约 1%–3% | 30 – 100 | 10 – 30 秒 |
| W-Wing / Finned X-Wing | 约 0.3%–1% | 100 – 300 | 30 秒 – 1.5 分钟 |
| **UR Type1/Type2** | 约 **< 0.5%** | **200 – 2,000+** | **1 – 10 分钟** |
| **特定形态的 AIC** | 约 **< 0.1%** | **1,000 – 10,000+** | **5 分钟 – 1 小时** |

> 注：上述比例为数独求解器社区长期实践的经验区间，实际值随"挖洞策略、对称性要求、提示数下限"而变化，量级结论稳定可靠。

**在移动端低端机上，以上耗时还需再乘以 3–5 倍。** 结论明确：**运行时实时生成高难度定向谜题，绝无可能。**

#### 3.2.3 教学关卡的额外要求（比难度筛选更苛刻）

教学关卡不只要求"需要用 Swordfish"，还要求：

- 该技巧出现在**教学上合适的时机**（不能在开局第一步就要求用 Swordfish，玩家还没填几个数）；
- 该技巧的**图形形态清晰美观**（三行三列排布不能过于分散，否则画出来的连线一团乱麻）；
- 使用该技巧前的**所有前置步骤都在玩家已学范围内**（第 2 章的关卡不能要求玩家先会第 4 章的技巧）；
- 使用该技巧后的**后续步骤能顺畅收尾**。

**这四条是"课程设计"约束，不是"生成算法"能满足的。** 随机生成 + 过滤在这里彻底失效。

### 3.3 「强制校验使用了目标技巧」的可实现性分析

#### 3.3.1 为什么严格意义上做不到

系统的可观测信息**仅限于操作事件流**：

```
[选中 r4c2] → [删除候选数 7] → [选中 r6c8] → [删除候选数 7] → [选中 r2c5] → [填入 3] → ...
```

而"玩家是否使用了 X-Wing"是一个**关于玩家心理状态的命题**。以下三类玩家产生的事件流可以**完全相同**：

1. 真正识别出 X-Wing 并据此删数的玩家；
2. 看过攻略、背下了这一步的玩家；
3. 随手删了两个候选数，恰好蒙对的玩家。

**没有任何算法能从相同的输入中区分出不同的输出。** 这是信息论层面的不可判定，不是工程投入能解决的问题。任何声称能做到的方案，本质上都是在做近似。

#### 3.3.2 ✅ 可落地的四层近似判定方案

**第 1 层：关键删数校验（Key Elimination Gate）—— 核心机制，必做**

关卡数据中预先标定目标技巧产生的**精确删数集合**（如"从 r4c2 和 r6c8 中删除候选数 7"）。玩家必须**完成这些特定的候选数删除操作**，关卡才判定"技巧已应用"。

- ✅ 完全可观测、可判定、无歧义
- ✅ 挡住了"完全不碰这个技巧就靠猜通关"的情况
- ⚠️ 挡不住"背答案"

**第 2 层：前置条件锁（Premature-Fill Lock）—— 必做**

对那些**只有在完成关键删数之后才能被逻辑确定**的单元格，在关键删数完成前**锁定其数字输入**。玩家若尝试提前填入，即时弹窗拒绝：

> 「你还没有获得填入该格的逻辑依据。请先找到本关的目标技巧。」

- ✅ 这是**打击"猜数绕过"最有效的一层**——猜数玩家的典型行为正是"直接把答案填进去"，此层直接封死该路径
- ✅ 完全可观测

**第 3 层：模式指认（Pattern Assertion）—— ⭐ 强烈推荐，但需客户拍板**

与其被动推断玩家意图，不如**主动要求玩家声明意图**。执行关键删数前，要求玩家：

1. 点击工具栏选择技巧类型（如「X-Wing」）；
2. 依次点选构成该技巧的关键格（如 X-Wing 的 4 个角点）；
3. 系统校验所选格是否确实构成一个合法的 X-Wing；
4. 校验通过后才解锁删数操作。

- ⭐ **这是把"不可观测的心理行为"转化为"可观测的 UI 行为"的唯一有效手段**，判定可信度从"弱"直接提升到"强"
- ⭐ 同时它本身就是**极佳的教学交互**——强迫玩家显式地把模式找出来，学习效果远好于默默删两个数
- ⚠️ **它改变了需求书 §2.4 描述的交互模型**（原文只提到"触摸选格 + 数字键盘 + 长按标记"），需要新增一套"技巧指认模式"UI
- ⚠️ 增加约 3–5 人日工作量

**第 4 层：试错惩罚（Anti-Undo-Scumming）—— 建议做**

试炼关中限制无限撤销（或记录错误次数）。带失误通过的关卡标记为「通过（有失误）」而非满分通过，需重刷才能拿到完美评价。防止玩家用"穷举 + 撤销"暴力试出答案。

#### 3.3.3 建议写入验收标准的降级口径（请客户书面确认）

> **验收试炼关「通过目标技巧完成」的判定标准：**
>
> 玩家同时满足以下条件即判定为通过：
> 1. 在正确的时机完成了目标技巧对应的**全部关键删数操作**；
> 2. **未在逻辑依据成立之前**填入受保护单元格的数字；
> 3. （若采纳第 3 层方案）**正确指认了构成目标技巧的关键单元格**；
> 4. 错误操作次数在允许范围内。
>
> **系统不保证、也在技术上无法保证识别玩家的内心推理过程。** 上述标准是在"仅可观测玩家操作行为"这一客观约束下，判定强度最高的可实现方案。

#### 3.3.4 一个重要的连带结论

第 1、2 层都要求关卡数据中**预先标定"关键删数集合"与"受保护单元格集合"**。这只能在**离线、人工审校的关卡数据**中完成——**再次印证 §3.2 的结论：教学关卡必须是预置盘面 + 预置解题脚本，不能是运行时生成的。**

### 3.4 求解器性能与 Isolate 需求（T-17）

| 场景 | PC 预估 | 低端 Android 预估（×3–5） | 是否需要 Isolate |
|---|---|---|---|
| 回溯求解一道良构谜题 | < 1–5 ms | < 25 ms | ❌ 不需要 |
| 唯一解校验（解数计数） | 5–20 ms | < 100 ms | ⚠️ 建议 |
| 单个简单技巧扫描（X-Wing / XY-Wing） | < 5 ms | < 25 ms | ❌ 不需要，可在主 isolate 实时跑 |
| 全技巧链扫描（含 AIC）求一次提示 | **10–500 ms** | **可达 1–2.5 s** | ✅ **必须** |
| 谜题生成（挖洞 + 评级） | 100–300 ms | 0.5–1.5 s | ✅ **必须** |

**结论与建议**：

1. **实时校验、候选数更新、高亮计算**：主 isolate 直接跑，无压力，可保证 16 ms 帧预算。
2. **AIC 提示计算、谜题生成、难度评级**：**必须放入 isolate**（`Isolate.run`），否则低端机必然卡顿掉帧。
3. **架构约束**：算法层必须是**纯 Dart、零 Flutter 依赖**——这一点需求书 §4 已经要求了，而它恰好也是 isolate 安全的前提（isolate 间传递的数据必须可序列化，不能携带 Flutter 对象）。建议在 CI 中加一条静态检查：**`lib/core/` 下禁止出现 `package:flutter` 的 import**，违反即构建失败。
4. **UX 兜底**：任何超过 300 ms 的计算必须显示加载指示；AIC 提示应设置**超时上限**（如 3 s），超时则降级为"本关提示暂不可用"而非无限转圈。
5. **性能预算需客户确认**：目标最低端设备是什么？（如"2019 年千元 Android 机"）这决定了 AIC 链长上限等参数的取值。

## 四、🟢 技术选型待确认项（含推荐）

### T-18　状态管理：Provider vs Riverpod

- ✅ **推荐：Riverpod 2.x**
- **理由**：
  1. **可测试性**——这是决定性因素。Riverpod 的 Notifier **不依赖 `BuildContext`**，可以脱离 Widget 树直接单元测试。本项目状态与算法强耦合（盘面状态、候选数、撤销栈、教学步进），需要大量状态层测试，Provider 的 `context` 依赖会让这些测试被迫变成 widget test，慢且脆。
  2. `ProviderScope.overrides` 可以一行代码注入固定盘面，测试夹具极其干净。
  3. 编译期安全，不会出现 Provider 的 `ProviderNotFoundException` 这类运行时错误。
- **代价**：学习曲线略陡；若启用 codegen 需引入 `build_runner`（**建议本项目不启用 codegen**，手写 Notifier 即可，避免拖慢开发循环）。
- **决策归属**：⚠️ **这是我方技术决策，不建议占用客户决策带宽。** 建议告知客户"我方选用 Riverpod"即可，无需其拍板。

### T-19　本地存储：sqflite vs isar vs 纯 JSON

- ✅ **推荐：不使用数据库。纯 JSON 文件 + `path_provider`（+ `shared_preferences` 存少量标量设置）**
- **理由（三条硬理由）**：
  1. **数据量根本用不着数据库**。全部持久化数据 = 约 40 关的进度状态 + 一份设置 + 错题本（数百条上限）+ 练习统计。总量在**几十 KB 到低个位数 MB** 量级。为此引入数据库是明确的过度设计。
  2. 🔴 **Isar 有两个硬伤**：①**维护活跃度存在明显风险**——原维护者已淡出，v4 长期停留在 alpha，对于一个需要长期维护的交付项目这是实质风险；②**Isar 桌面端需要原生 `isar.dll`，其默认初始化方式是运行时联网下载核心库**（`Isar.initializeIsarCore(download: true)`），**这与需求书 P0 的「完全离线」要求直接冲突**。虽可手动打包 DLL 规避，但需为 Windows/macOS 各自管理原生产物，徒增复杂度。
  3. **sqflite 在桌面端不能直接用**——必须换成 `sqflite_common_ffi` 并随包分发 `sqlite3.dll`（Windows）/`.dylib`（macOS），同样是每平台的原生资产管理负担。
- **推荐方案的优势**：纯 Dart 零原生依赖 → 5 个平台行为完全一致 → 天然完全离线 → 测试时可注入内存文件系统 → 数据文件可读可 diff 可人工修复。
- **实现要点**：原子写入（写临时文件 → rename）、Schema 版本号字段、单一 `ProgressRepository` 接口。
- **扩展保障**：保留 `ProgressRepository` 抽象接口，未来若错题本数据量意外膨胀，可无损替换为 `sqflite_common_ffi` 实现，业务层零改动。这正好满足需求书 §4「预留扩展接口」的要求。
- **需客户确认**：接受"不使用数据库"这一偏离需求书 §3 技术栈描述的选择。（需求书原文写的是 "sqflite/isar"，我方认为这是过度设计，建议简化）

### T-20　Flutter / Dart 版本锁定

- ✅ **推荐：在项目启动日锁定当时的 Flutter **stable** 最新版，并在整个项目周期内不做大版本升级**
- **理由**：需求书写的 "Flutter 3.x" 跨度极大（3.0 至 3.3x 之间，Android Gradle 插件、Kotlin DSL 迁移、Web 渲染器策略、Impeller 默认开关都发生过破坏性变化），必须锁死到具体版本号。
- **落地方式**：
  - `pubspec.yaml` 中写死 `environment: { sdk: '>=3.x.0 <4.0.0', flutter: '>=3.x.0' }`
  - **推荐引入 FVM**（Flutter Version Management）并提交 `.fvmrc`，保证任何机器上构建结果一致
  - 开发文档中明确记录精确版本号与 `flutter doctor -v` 的期望输出
- **连带需确认的平台下限（客户需给出目标用户设备范围）**：
  - Android `minSdkVersion`：**建议 23**（Android 6.0，兼容性与覆盖率的最佳平衡点）
  - Android `targetSdkVersion`：跟随 Google Play 当年要求
  - Windows 最低版本：Flutter 官方下限为 **Windows 10 1809+**
  - JDK：**锁定 JDK 17（Temurin）**，AGP 8.x 要求

### T-21　教学关卡数据存储格式

- ✅ **推荐：JSON 资源文件（`assets/curriculum/`），一关一文件 + 一份 `index.json` 清单**
- **对比**：

| 方案 | 可扩展性 | Git 可审阅 | 非程序员可编辑 | 是否需重编译 | 评价 |
|---|---|---|---|---|---|
| 硬编码 Dart 常量 | 差 | 差（大段代码） | ❌ | ✅ 需要 | ❌ 不推荐 |
| **JSON 资源文件** | **优** | **优（纯文本 diff）** | **✅** | ⚠️ 需重打包（资源变更） | ✅ **推荐** |
| 数据库 | 中 | ❌ 二进制不可 diff | ❌ | 否 | ❌ 迁移痛苦、内容不可审阅 |

- **理由**：直接满足需求书 §4「便于新增技巧与关卡」。新增一关 = 加一个 JSON 文件 + 在 index 中登记一行，**无需改动任何逻辑代码**。文本格式可在 Git 中逐行 review，课程设计人员（非程序员）也能参与编写。
- **⭐ 附带的高价值做法**：写一个 CI 测试，**遍历所有关卡 JSON，逐个用引擎回放其预置解题脚本，验证每一步的技巧识别与删数都与标注一致**。这样任何一次算法改动若破坏了某关的可解性，CI 立刻报警。这条测试的性价比极高，强烈建议纳入。
- **注意**：assets 是只读的，玩家进度数据写入 T-19 的 JSON 存储，二者分离。

### T-22　Web 端是否本期交付

- ✅ **推荐：本期明确不做，作为后续独立变更单**
- **理由**：
  1. 需求书自己写的是「**可选** Web」，且未列入 P0/P1/P2 任何优先级——说明客户自己也没想清楚。
  2. **"HTML renderer 包体小"这个退路已经不存在了**：Flutter 自 3.29 起移除了 HTML renderer，Web 端只剩 CanvasKit / skwasm，意味着**必然引入约 1.5–2 MB 的额外 wasm/js 下载**（外加 CJK 字体，若不做子集化可再增数 MB）。首屏体验代价明确。
  3. `CustomPaint` 在 Web 上虽有 CanvasKit 保证保真度，但**文本渲染、字体回退、手势细节仍与原生存在差异**，需要独立的 QA 轮次。
  4. Web 的"离线"是 Service Worker/PWA 语义，与原生离线是**两套完全不同的实现与验收标准**。
  5. Web 是第三套交互模式（鼠标+键盘+可能的触屏），QA 矩阵直接扩大。
- **结论**：它不是"顺便就能出"的，需要独立预算。若客户坚持本期要，请明确它的优先级并追加工期。

### T-23　中文字体策略（承接 T-06）

- **问题**：Flutter 默认使用系统字体渲染中文。Windows（微软雅黑）、Android（思源黑体系）、iOS（苹方）的中文字形差异明显，**跨平台视觉一致性无法保证**。
- **选项**：
  - **A. 依赖系统字体**：包体积零增加，但三端中文观感不一致。
  - **B. 内置 Noto Sans SC**：全量约 10 MB（apk 显著变大）；**子集化后可压至 1–3 MB**（需构建期字体子集化流程）。视觉完全一致。
- ✅ **推荐：A（依赖系统字体）**，除非客户对品牌视觉一致性有明确要求。理由：本项目是工具/教学类应用而非品牌营销类，10 MB 的包体增量不划算；若客户坚持一致性，选 B 并做子集化。
- **需客户确认**：是否接受三端中文字形存在差异。

**T-25　⚠️「技巧识别准确率」必须重新定义**

需求书要求测试「各技巧识别准确率」，但**"准确率"作为单一数字在这里是没有意义的**，必须拆成两个指标，且二者的要求截然不同：

| 指标 | 含义 | 目标 | 为什么 |
|---|---|---|---|
| **精确率 Precision** | 报出的每一个模式都真实成立，产出的每一个删数都逻辑正确 | 🔴 **必须 100%，无妥协** | 一次错误的删数会**直接把谜题变成死局**，玩家怎么做都解不开。这是最严重的一类 Bug，零容忍 |
| **召回率 Recall** | 盘面上存在的目标模式能被找出的比例 | **≥ 95%** | 漏掉一个罕见变体，后果只是"提示功能少给了一条建议"，玩家可用其他技巧继续。可以容忍 |

**这是一个刻意不对称的指标设计，需要客户理解并认可。**

**T-26　标注盘面集从哪来**

「识别准确率」的度量需要一个**带标准答案的测试盘面集**，这不存在现成免费资源，必须我方构建：

- **规模建议**：每项技巧 ≥ 20 个标注用例 × 10 项技巧 = **≥ 200 个用例**。每个用例包含：盘面、候选数状态、期望识别出的模式格、期望的删数集合。
- **来源**：① 用我方离线出题工具批量产出候选 → ② 人工逐个核验标注。**预估 3–5 人日**，需求书未计入。
- **⭐ 强烈建议补充"健全性模糊测试"（性价比最高的一条测试）**：随机生成 N（如 10,000）道**已知唯一解**的谜题，让所有技巧在其上自由运行，**断言任何技巧产出的删数，其被删的候选数都不等于该格的正确答案**。这条测试能自动捕获"错误删数"这一最致命的 Bug 类别，编写成本极低（< 半天），建议必做。
- **需客户确认**：是否允许我方以第三方开源求解器（如 HoDoKu 等）的输出作为**交叉校验参考**？（注意：仅用于验证我方实现的正确性，不复制其代码或数据，但仍建议客户书面认可以规避授权争议。）

## 六、给客户的一句话总结

> 这份需求写得很专业，数独算法部分我们有把握做好；但**在开工前有三件事必须先解决**：
>
> **第一，交付环境是零。** 这台开发机上 Flutter、JDK、Android SDK、Visual Studio 一个都没装，现在连 `flutter --version` 都跑不出来，需要先补齐约 20–28 GB 的工具链，其中 Visual Studio 的安装需要管理员权限、必须由贵方或机器所有者介入。**更重要的是：macOS 和 iOS 的安装包在 Windows 电脑上物理不可能打出来**——这是 Apple 的硬性限制，不是工期或能力问题。如果贵方不提供 Mac 设备和 Apple 开发者账号，这两个平台的产物必须从合同里拿掉。
>
> **第二，有两条需求按现在的写法做不到，需要降级。** ①「实时生成一道必须用 Swordfish 才能解开的题」——这类谜题在随机生成中的命中率约千分之一到百分之一，现场生成一道要等几分钟到一小时，必须改成**离线预先生成好的题库**；②「强制校验玩家必须用目标技巧、猜数就不给过」——玩家脑子里怎么想的系统看不见，严格意义上无法判定，我们能做到的是**校验关键删数 + 锁死提前填数 + （推荐新增）要求玩家先把技巧的关键格点出来**，这套组合拳能挡住绝大多数猜数行为，但请接受它是"很强的近似"而不是"100% 识别"。
>
> **第三，工作量的重心和文档给人的印象不一样。** 「高级技巧识别引擎」在需求书里只是一个小条目，但它实际占了整个项目技术难度的六成以上，其中**光「基础 AIC」一项的工作量就约等于其余九项技巧之和**，而且 AIC、W-Wing、Finned/Sashimi、唯一矩形这几项**在业界本身就有多套实现口径**，需要贵方和我们一起把口径敲定下来，否则做完了才发现理解不一致，只能返工。
>
> **我的建议是：先花一周做 M0——把工具链装好，用一个空白工程打出 Windows 安装包和安卓 apk 交给您装上试试。** 这一步走通了，后面的算法我们有信心；这一步走不通，做再多功能也交付不出去。**先把交付这条路打通，再谈盖房子。**
